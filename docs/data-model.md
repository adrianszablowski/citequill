# Data model

Postgres in one Supabase project, separate from the owner's other applications. Access only from the server. TypeScript types come from `supabase gen types`, never by hand. Every table except `users`, `audit_queue` and `audit_renders` has `project_id`; it is the only boundary between projects. `audit_queue` and `audit_renders` reach their project through `audit_id`.

The column names below are concepts, not SQL. The migration implements them; when they differ, the migration is wrong. A table or column enters the migration of the step in [`product.md`](product.md) that first reads it, so an early migration holds a subset of the tables here.

## Site pages and audits

| Table                 | Columns                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `site_pages`          | `id`, `project_id`, `url` (unique per project), `locale`, `status_code`, `final_url`, `redirect_to`, `is_indexable`, `is_blocked` (robots.txt disallowed the URL, so the audit did not fetch it), `canonical_url`, `title`, `body_hash`, `in_sitemap`, `hreflang` (JSON, the page's alternates), `click_depth`, `inbound_links`, `raw_extract` (JSON, the fields the render step compares, set for the sample), `page_id` (set when Citequill wrote the page, matched by its computed path), `first_seen_at`, `last_seen_at`, `is_gone` (set by a complete audit that did not meet the page), `last_audit_id` |
| `audits`              | `id`, `project_id`, `run_id`, `score`, `is_gated`, `is_partial` (the site has more pages than the audit read, or the owner stopped it), `checks_scored`, `checks_total`, `pages_read`, `pages_indexable`, `pages_rendered`, `severity_3`, `severity_2`, `severity_1`, `hints`, `questions`, `duration_s`, `request_count`, `host_429_count`, `host_5xx_count`, `sandbox_cpu_s`, `sandbox_gb_h`, `sandbox_names` (JSON), `robots_rules` (JSON, the parsed robots.txt), `render_token_hash`, `render_token_expires_at`, `created_at`                                                                            |
| `audit_queue`         | `audit_id`, `url`, `depth` (empty for a URL only a sitemap lists), `state` (`queued`, `read`, `blocked`), `in_sitemap`, `inbound_links` (the pages linking to it so far); primary key from the first two; the crawl's frontier, deleted when the audit ends                                                                                                                                                                                                                                                                                                                                                   |
| `audit_check_results` | `audit_id`, `project_id`, `check`, `pages_checked`, `pages_failed`, `pages_intended`; primary key from `audit_id` and `check`                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| `audit_findings`      | `id`, `audit_id`, `project_id`, `site_page_id` (empty for a site-level finding), `check`, `severity`, `subject` (an image `src`, a link `href`, a sitemap URL), `selector` (from id, classes and tag, never a position), `snippet`, `detail` (JSON, what the check saw: the status code, the hop chain, the two values that differ), `fingerprint` (hash of `check`, `site_page_id`, `subject`, `selector`), `is_intended`                                                                                                                                                                                    |
| `audit_renders`       | `audit_id`, `site_page_id`, `result` (JSON, the compared fields of the rendered page), `posted_at`; primary key from the first two                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| `audit_marks`         | `id`, `project_id`, `check`, `url` (empty for a selector or a check mark), `selector` (empty for a URL or a check mark), `note`, `created_at`; unique on `project_id`, `check`, `url`, `selector`                                                                                                                                                                                                                                                                                                                                                                                                             |

`site_pages` is the one list of the site's URLs: the connect crawl starts it, with `is_indexable` read from the robots meta, and every audit updates it in place, so the by-page view of an older audit shows the page as it is today. Host, trailing slash and case variants are distinct rows, because `host-variants` needs them; fragments are dropped. Rows are never deleted. `crawled_pages` keeps the content of the 50 pages the crawl read for facts. `check` is an identifier from the catalogue in [`audit.md`](audit.md), so a finding, a mark and a check result name the same thing. `audit_check_results` holds the denominators the score needs and the passes the report shows, such as decorative images; `pages_intended` counts the pages whose every failing element is intended. `audit_findings` holds failures only, with the snippet and selector of the failing element and no page HTML; `fingerprint` is what the comparison of two audits joins on. `audit_renders` holds the rendered extracts the render route posts, never HTML. An audit's cost is its run's `cost_usd`.

The queue holds what the walk learns about a URL while the audit runs: its click depth, whether a sitemap lists it and how many pages link to it. `site_pages` takes the values when the page is read, and the inbound count again when the audit ends, so a count from one audit never mixes with the next and an audit that does not finish leaves the pages it did not reach as they were.

Retention is a sweep at the end of every audit: the audit that ends and the most recent other audit of the project whose run is not `running`, the two most recent once the run ends, keep their rows in `audit_queue` (emptied for all), `audit_check_results`, `audit_findings` and `audit_renders`; the rows of every older audit are deleted, and the `audits` row keeps its score and counters, so `last_audit_id` never dangles.

A mark matches by string equality: a URL mark a finding with that URL and check, a selector mark one with that selector and check, a check mark every finding of that check; a site-level finding, which has no page, matches a URL mark by its subject. The scoring has one home, the server's code: it applies the marks, counts the check results and computes the score, the gate and the counters, and `score_audit`, a `security definer` function, writes them: the score, `is_gated`, `checks_scored`, `checks_total`, the five counters, `is_intended` on every finding of the audit and the audit's rows of `audit_check_results`. It writes only to the project's most recent audit, and for a signed-in user only to an audit of their own project whose run is not `running`; the Workflow's Score step calls it with the service role while its run still is. So the owner's click on a mark recomputes the latest audit, Stop scores a stopped audit, because the owner's session has no write to `audits` of its own, and older audits keep the score they had. Every later audit applies the marks itself at scoring time. Run the audit creates the `audits` row through `create_audit`, Stop marks it partial through `stop_audit` and scores it through `score_audit`; all three are `security definer` functions that the signed-in user may call. `create_audit` acts only on a run with `trigger` `audit` of the caller's own project, and `stop_audit` only on an audit of the caller's own project whose run Stop has already ended as `failed`; Stop calls `stop_audit` and `score_audit` only when its own update ended the run, so a run that finished on its own just before the click keeps its complete audit and its complete score.

The two views of the findings read through `audit_check_list` and `audit_page_list`, SQL functions that group one audit's findings by check, with its pages failing and its pages intended, and by page, with its findings by severity, because PostgREST cannot group or sort by a count. They run as the caller, so the row level security of `audit_findings` and `site_pages` decides what they return.

The render token is minted in the Workflow step that creates the sandboxes, stored as a hash with an expiry equal to the step's wait deadline, and cleared when the sandboxes end or the owner stops the audit. The render route accepts a post only while the run is `running`, the token matches and the URL is in the render set, and a second post for one URL once; a leaked token can forge render results for one audit until it expires and read nothing. The route writes with the admin client, the one route a user never calls that does.

## Pages

| Table   | Columns                                                                                                                                                                                                                                                                                                                                                                                                                    |
| ------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `pages` | `id`, `project_id`, `kind_id`, `locale`, `slug`, `translation_group_id`, `status` (`draft`, `published`, `unpublished`), `title`, `meta_title`, `meta_description`, `excerpt`, `body_md`, `body_html`, `faq` (list of question and answer), `sources` (list of title and URL), `tags`, `author_id`, `reading_minutes`, `check_note`, `redirect_to`, `run_id`, `published_at`, `updated_at`, `unpublished_at`, `created_at` |

Locale versions of one page share a `translation_group_id`; the API derives `translations` from it. The full path of a page is not a column: it is the locale's `base_url` plus the kind's `url_prefix` plus the `slug`, computed in one place in the code. `body_html` is produced from `body_md` at publishing. `check_note` is empty when the page passed the check. `redirect_to` is empty for 410 and filled for 301; only `unpublished` pages have it, so the list of redirects is a query, not a table.

## Runs and reports

| Table     | Columns                                                                                                                                                                                                                                                                                                                                                                                                                 |
| --------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `runs`    | `id`, `project_id`, `trigger` (`crawl`, `weekly`, `manual`, `audit`), `topic`, `kind_id` and `locale` (for `manual`), `status` (`running`, `finished`, `failed`), `plan` (topics with reasoning and sources), `input_tokens`, `output_tokens`, `cost_usd`, `error`, `workflow_run_id`, `started_at`, `progressed_at` (written by every step; the stall rule reads it, with `started_at` as the fallback), `finished_at` |
| `reports` | `id`, `project_id`, `run_id`, `week_start`, `body_md`, `created_at`                                                                                                                                                                                                                                                                                                                                                     |

Every model call adds its tokens and cost to its run through the database function `add_run_usage`, which adds in place, so calls that run in parallel never overwrite each other's sums; only the service role may call it. This is the only place the dashboard and a future spending limit read the cost from, and only the operator sees it. `cost_usd` means what the run cost Citequill: model tokens, the web search tool and, for an audit, the sandbox's CPU and memory, each priced from the unit prices kept in one place. The crawl on connection is a run with `trigger` `crawl`, so its model calls land in the same place, and its `status` and `error` are what the progress page shows. An audit is a run with `trigger` `audit` for its status, its progress and Stop, with its score and counters in `audits`.

## Analytics

| Table                 | Columns                                                                                                                                                                                                                                                                                                             |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `events`              | `id`, `project_id`, `occurred_at`, `visitor_hash`, `name` (`pageview` or the name of a custom event), `path`, `page_id` (when the path is a Citequill page), `referrer`, `referrer_group` (`search`, `ai`, `social`, `site`, `direct`), `country`, `utm_source`, `utm_medium`, `utm_campaign`, `amount`, `currency` |
| `search_console_rows` | `project_id`, `date`, `query`, `page`, `country`, `clicks`, `impressions`, `position`; primary key from the first five columns                                                                                                                                                                                      |

`events` is partitioned by the month of `occurred_at`. `visitor_hash` is a SHA-256 of the daily salt, IP, user agent and `site_id`; the salt is an HMAC of the server secret and the date, so there is no salt table, and yesterday's visitor cannot be linked to today's. `amount` and `currency` are empty in the MVP and wait for revenue from the backlog.
