# Data model

Postgres in one Supabase project, separate from the owner's other applications. Access only from the server. TypeScript types come from `supabase gen types`, never by hand. Every table except `users`, `audit_queue` and `audit_renders` has `project_id`; it is the only boundary between projects. `audit_queue` and `audit_renders` reach their project through `audit_id`.

The column names below are concepts, not SQL. The migration implements them; when they differ, the migration is wrong. A table or column enters the migration of the step in [`product.md`](product.md) that first reads it, so an early migration holds a subset of the tables here.

The owner cannot select the two webhook secrets, so a secret is shown once, when it is made. `project_locales.locale` holds the canonical form, which the crawl and Settings write; the step 5 migration rewrites the lowercased values stored before it. `bot_secret` is stored in clear, because Settings shows it again whenever the owner writes a firewall rule, and it only lets a crawler through a firewall the owner controls.

`site_pages` is the one list of the site's URLs: the connect crawl starts it, with `is_indexable` read from the robots meta, and every audit updates it in place, so the by-page view of an older audit shows the page as it is today. Host, trailing slash and case variants are distinct rows, because `host-variants` needs them; fragments are dropped. Rows are never deleted. `crawled_pages` keeps the content of the 50 pages the crawl read for facts. `check` is an identifier from the catalogue in [`audit.md`](audit.md), so a finding, a mark and a check result name the same thing. `audit_check_results` holds the denominators the score needs and the passes the report shows, such as decorative images; `pages_intended` counts the pages whose every failing element is intended. `audit_findings` holds failures only, with the snippet and selector of the failing element and no page HTML; `fingerprint` is what the comparison of two audits joins on. `audit_renders` holds the rendered extracts the render route posts, never HTML. An audit's cost is its run's `cost_usd`.

The queue holds what the walk learns about a URL while the audit runs: its click depth, whether a sitemap lists it, how many pages link to it and the first 5 of them. `site_pages` takes the values when the page is read, and the inbound count again before the site checks run, so a count from one audit never mixes with the next and an audit that does not finish leaves the pages it did not reach as they were. `audit_resources` is the second frontier: the images, `og:image`s, scripts, stylesheets and external links the pages hold, which the resources step checks after the last page is read; a stopped audit never checks them.

Retention is a sweep at the end of every audit: the audit that ends and the most recent other audit of the project whose run finished, the two the comparison reads, keep their rows in `audit_queue` and `audit_resources` (both emptied for all), `audit_check_results`, `audit_findings` and `audit_renders`; the rows of every older audit are deleted, and the `audits` row keeps its score and counters, so `last_audit_id` never dangles.

A mark matches by string equality: a URL mark a finding with that URL and check, a selector mark one with that selector and check, a check mark every finding of that check; a site-level finding, which has no page, matches a URL mark by its subject. The scoring has one home, the server's code: it applies the marks, counts the check results and computes the score, the gate and the counters, and `score_audit`, a `security definer` function, writes them: the score, `is_gated`, `checks_scored`, `checks_total`, the five counters, `checks_run`, `score_difference`, `findings_fixed` and `findings_new`, `is_intended` on every finding of the audit and the audit's rows of `audit_check_results`. It writes only to the project's most recent audit, and for a signed-in user only to an audit of their own project whose run is not `running`; the Workflow's Score step calls it with the service role while its run still is. So the owner's click on a mark recomputes the latest audit, Stop scores a stopped audit, because the owner's session has no write to `audits` of its own, and older audits keep the score they had. Every later audit applies the marks itself at scoring time. Run the audit creates the `audits` row through `create_audit`, Stop marks it partial through `stop_audit` and scores it through `score_audit`; all three are `security definer` functions that the signed-in user may call. `create_audit` acts only on a run with `trigger` `audit` of the caller's own project, and `stop_audit` only on an audit of the caller's own project whose run Stop has already ended as `failed`; Stop calls `stop_audit` and `score_audit` only when its own update ended the run, so a run that finished on its own just before the click keeps its complete audit and its complete score.

The three views of the findings read through `audit_check_list`, `audit_page_list` and `audit_image_list`, SQL functions that group one audit's findings by check, with its pages failing and its pages intended, by page, with its findings by severity, and by image subject, with its alts, ancestors, checks, pages and pages intended, because PostgREST cannot group or sort by a count. `audit_image_list` takes the ids of the image checks from its caller, so the list of them keeps its one home in the code. They run as the caller, so the row level security of `audit_findings` and `site_pages` decides what they return.

The render token is minted in the Workflow step that creates the sandboxes, stored as a hash with an expiry equal to the step's wait deadline, and cleared when the sandboxes end or the owner stops the audit. The render route accepts a post only while the run is `running`, the token matches and the URL is in the render set, and a second post for one URL once; a leaked token can forge render results for one audit until it expires and read nothing. The route writes with the admin client, as the Content API's routes and the publishing module do; no user calls it.

`pages` is the working copy, which the editor saves, and `published_pages` the version the site shows, which the API, the sitemaps and the webhook read. A page has a published version from its first publication on, and its `status` says whether it is live: a live page is one whose `status` is `published`. Wherever the API, the sitemaps or `alternates` read `published_pages`, they read live pages only.

The publishing module in [`workflow.md`](workflow.md) is the only writer of `published_pages`, with the admin client, through SQL functions granted to the service role alone; no SQL function the browser can call takes HTML. On `pages` a signed-in owner may update only the fields the editor holds, by column grants. A trigger on `pages` sets `updated_at` and `content_hash` on every insert and update, so a save in the owner's session moves `updated_at`. The trigger also refuses a new `slug` on a page published before. `content_hash` has one home, the database function `page_content_hash`, which the trigger calls. The working copy has no reading time: `readingMinutes()` computes it from the word count of the rendered body wherever it is shown, and the publishing module stores it in the published version. The author of a page, a kind and a published version belongs to the row's project, by a foreign key on `author_id` and `project_id`; deleting an author sets only `author_id` to null. `publish_pages` writes the author a page goes live with, its kind's when it has none, into the working copy, so after a publication both versions hold the same author. `status`, `redirect_to`, `published_at` and `unpublished_at` are written by the server alone. The owner may read the `published_pages`, `webhook_deliveries` and `indexnow_pings` rows of their own projects, which the Pages table and the Settings log need; deliveries and pings are kept 90 days.

The API reads through SQL functions that take a key's hash, return only that key's project and only live pages, and are granted to the service role alone. The keyless XML sitemap reads through one more such function, which takes a `site_id` and a host and returns only the live pages' URLs, dates and alternates on that host; an unknown `site_id` or a host outside the project's locales returns nothing, and the route answers 404.

Locale versions of one page share a `translation_group_id`; the API derives `alternates` from the group's live versions. The path of the working copy is not a column: it is the locale's `base_url` plus the kind's `url_prefix` plus the `slug`, computed in one place in the code. The published version keeps the `path` and `url` it was first published under, so a later change of a base URL or a prefix moves no live page; Publish refuses a page whose computed path no longer matches. `body_html`, `toc`, `word_count` and `body_hash` are produced from `body_md` at publishing; the step 5 migration drops `pages.body_html`, because the rendered HTML lives only in the published version. Two hashes compare a working copy with what went out. `content_hash` covers every field the editor holds: a page has unpublished changes when its `content_hash` differs from its published version's. `text_hash` covers the title, `body_md` and the FAQ: `modified_at` moves only when a publication's `text_hash` differs from the version it replaces, so a change of the meta title, the meta description, the excerpt, the tags, the sources or the author leaves the content date alone. `updated_at` of the published version moves on every publication, when the page is unpublished, when the group's `alternates` change, and when the owner edits in Settings an author, the organization, a kind or a locale the page shows. The list's order and cursor read `pages.published_at`, the first publication, which a later publication never moves. `check_note` is empty when the page passed the check. `redirect_to` is empty for 410 and filled for 301; only `unpublished` pages have it, so the list of redirects is a query, not a table. `indexnow_pings` holds every ping with its answer, so the last ping of a URL, which a new ping waits 10 minutes after, and the count of 429 answers are queries.

Every model call adds its tokens and cost to its run through the database function `add_run_usage`, which adds in place, so calls that run in parallel never overwrite each other's sums; only the service role may call it. This is the only place the dashboard and a future spending limit read the cost from, and only the operator sees it. `cost_usd` means what the run cost Citequill: model tokens, the web search tool and, for an audit, the sandbox's CPU and memory, each priced from the unit prices kept in one place. The crawl on connection is a run with `trigger` `crawl`, so its model calls land in the same place, and its `status` and `error` are what the progress page shows. An audit is a run with `trigger` `audit` for its status, its progress and Stop, with its score and counters in `audits`.
