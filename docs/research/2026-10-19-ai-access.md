# AI agents, edge blocks and AI-facing signals (fetched 2026-10-19)

On 19 October 2026 we fetched the crawler pages of OpenAI, Anthropic, Perplexity, Microsoft Bing, Apple, Mistral, DuckDuckGo, Amazon, Meta, Google and Common Crawl. We also fetched Cloudflare's developer docs and blog, Vercel's docs, knowledge base and blog, the IndexNow documentation and FAQ, the IndexNow, Rank Math and Yoast pages, Google Search Central, Bing Webmaster Tools help, the Claude Code docs, the OpenCode source on GitHub and llmstxt.org. Most pages were read as raw HTML with `curl`. Cloudflare and Vercel pages were read as Markdown. Bing's help pages, Meta's crawler page and contentsignals.org render with JavaScript, so we read them in a browser. Every quote below comes from one of those fetches, with its URL. Where a page shows a date, we give it. Where a vendor page is silent, we say so. Third-party sources and our own live checks are labelled as such and kept apart from vendor documentation.

## 2. How Cloudflare and Vercel mark a blocked or challenged request

### Cloudflare challenge pages

Source: https://developers.cloudflare.com/cloudflare-challenges/challenge-types/challenge-pages/detect-response/ (last updated May 5, 2026).

- "the Challenge Page response (regardless of the Challenge Page type) will have the `cf-mitigated` header present and set to `challenge`."
- "For the `cf-mitigated` header, `challenge` is the only valid value. The header is set for all Challenge Page types."
- "Regardless of the requested resource-type, the content-type of a challenge will be `text/html`."

The challenge docs do not give the status code. The nearest statement is on the Error 403 page (https://developers.cloudflare.com/support/troubleshooting/http-status-codes/4xx-client-error/error-403/, last updated Sep 28, 2026): "A `403` response with Cloudflare branding in the response body may be triggered by: WAF Custom or Managed Rules with the challenge or block action." As third-party corroboration, OpenCode's source treats `response.status === 403 && response.headers["cf-mitigated"] === "challenge"` as a Cloudflare challenge.

Other markers Cloudflare documents:

- the `cf_clearance` cookie; the challenge pages page names it in its Turnstile pre-clearance note, where "the Turnstile widget issues a persistent clearance cookie (`cf_clearance`) upon successful human verification" (https://developers.cloudflare.com/cloudflare-challenges/challenge-types/challenge-pages/)
- `window._cf_chl_opt`, where "Cloudflare will set `cTplC: 1` … when a custom template is in use" (https://developers.cloudflare.com/cloudflare-challenges/challenge-types/challenge-pages/additional-configuration/)
- custom template tokens such as `::CF_WIDGET_BOX::` and `::RAY_ID::` (same page)
- the rules field values `"managed_challenge" "iuam" "legacy_challenge" "country_challenge"` for `cf.response.error_type`; this field is server-side and not visible to a client

The default page's visible title and wording are not documented on the pages we fetched.

### Cloudflare blocks

- No Cloudflare page we fetched documents a response header that marks a plain block. `cf-mitigated` is documented for challenges only.
- WAF custom rule blocks: "The default response code is 403." A custom response can use "an HTTP status code for the response, in the range 400-499" and the types `text/html`, `text/plain`, `application/json` or `text/xml`. This "is only available on Pro plans and above" (https://developers.cloudflare.com/waf/custom-rules/create-dashboard/, modified 2026-10-08).
- AI Crawl Control blocks: "When you block a crawler in AI Crawl Control, the system creates or updates a WAF custom rule on your zone to enforce that block." On paid plans the owner can set the code to "`403 Forbidden`" or "`402 Payment Required`" and "write a custom message (HTTP response body)" in plain text. The page does not state a default code or body; the WAF default above is 403 (https://developers.cloudflare.com/ai-crawl-control/features/manage-ai-crawlers/, last updated Jul 28, 2026).
- Redirects for AI Training, from 17 April 2026: "AI training crawlers that request a page with a canonical tag pointing elsewhere receive a 301 redirect to the canonical version." This is on Pro, Business and Enterprise (https://developers.cloudflare.com/ai-crawl-control/changelog/).

### Cloudflare Search, Agent and Training controls since 15 September 2026

Source: Cloudflare blog, "Have it both ways: stay discoverable in search while disallowing AI training", September 15, 2026 (https://blog.cloudflare.com/accountable-mixed-use-ai-crawlers/).

The three behaviours:

- "Search - crawling to build a search index."
- "Training - crawling to train or fine-tune a model."
- "Agent - user-directed agents visiting a page on behalf of a human, such as chat fetch bots and browser-use agents."

The settings, quoted:

- "Allow: All crawlers are allowed, unless blocked by another setting or a WAF rule."
- "Disallow AI Training: Bot Preference Sync publishes the applicable no-training preference in robots.txt. Accountable mixed-use crawlers remain allowed for search. Every other training crawler is blocked". It "is only available as a setting for Training, not Search or Agent."
- "Block on pages with ads: Crawlers, including mixed-use crawlers, are blocked only on pages detected to be serving an ad."
- "Block: All crawlers, including mixed-use crawlers, are blocked."

What changed on 15 September 2026:

- "Block and Block on pages with ads now apply to mixed-use crawlers, including Applebot, Bingbot, and Googlebot, so either setting impacts search as well as training."
- "“Block AI Bots” will be deprecated in favor of the more granular Search, Training, and Agent controls."
- "Managed Robots.txt will be deprecated in favor of Bot Preference Sync."

Presets for new domains, from the blog's table:

| Setting | Site does not monetize using ads | Site is monetized using ads |
| --- | --- | --- |
| Preference Sync | Enabled | Enabled |
| Search | Allow | Allow |
| Training | Allow | Disallow AI Training |
| Agent | Allow | Block on pages with ads |

Existing domains that never used the granular controls migrate from the legacy "Block AI" setting. "Disabled" becomes Allow for all three. "Block" and "Block on pages with ads" both become Search Allow, Training Disallow AI Training, Agent Block on pages with ads. Domains that had already set the granular controls keep them, except that a Training "Block" or "Block on pages with ads" becomes "Disallow AI Training".

The docs page does not match the blog. https://developers.cloudflare.com/bots/additional-configurations/block-ai-bots/ (last updated Jul 1, 2026) still says: "On September 15, 2026, Cloudflare will set updated defaults for new domains: bots classified as Training or as Agent will be blocked on pages that display ads, and Search will remain allowed." The blog's preset makes that true only for sites that run ads.

Bing is the exception for robots.txt: "selecting Disallow AI Training will not automatically convey a no-training preference to Bing through robots.txt." Microsoft is building robots.txt support "targeted for early 2027" (same blog).

### Vercel

Sources: https://vercel.com/docs/vercel-firewall/firewall-concepts, https://vercel.com/docs/vercel-firewall/attack-mode (the `attack-challenge-mode` URL redirects here), https://vercel.com/docs/bot-management, https://vercel.com/docs/vercel-firewall/vercel-waf/managed-rulesets and https://vercel.com/docs/vercel-firewall/vercel-waf/custom-rules. None shows a date.

- Deny: "A `403 Forbidden` response is returned." "The request does not reach your application."
- Challenge: "visitors see a Vercel Security Checkpoint screen". "Only human visitors using a web browser can pass the challenge". "Direct API calls (e.g., from scripts, cURL, or Postman) will fail if they require challenge validation." The docs give no status code for a challenge.
- Rate limiting can follow up with an action "that logs, denies, challenges, or returns a 429 response."
- Attack Mode: "visitors must complete a security challenge before accessing your site, while known bots (like search engines and webhook providers) are automatically allowed through." "Search engine crawlers like Googlebot are automatically allowed through Attack Mode without being challenged."
- Bot protection managed ruleset: "The ruleset is inactive by default." In challenge mode "the Vercel WAF will serve a JavaScript challenge to traffic that is unlikely to be a browser." It "automatically excludes verified bots".

`x-vercel-mitigated` is not documented. ## 3. Cloudflare Pay Per Crawl

Sources: https://developers.cloudflare.com/ai-crawl-control/features/pay-per-crawl/what-is-pay-per-crawl/ (last updated Jul 28, 2026) and https://developers.cloudflare.com/ai-crawl-control/features/pay-per-crawl/use-pay-per-crawl-as-ai-owner/crawl-pages/ (last updated Apr 23, 2026). The feature is "currently in closed beta".

- An unpaid request gets a 402: "Each time an AI crawler requests content, they either present payment intent via request headers for successful `HTTP 200` access, or receive an `HTTP 402 Payment Required` response with pricing."
- The documented example:

  ```txt
  HTTP/2 402
  date: Fri, 06 Jun 2025 08:42:38 GMT
  crawler-price: USD 0.01
  ```

Exact header names:

| Header | Direction | Meaning (quoted) |
| --- | --- | --- |
| `crawler-price` | response | "specifies the cost to access the content" |
| `crawler-exact-price` | request | "the exact price the AI crawler is configured to pay for access" |
| `crawler-max-price` | request | "the maximum price the AI crawler is configured to pay for access on any content" |
| `crawler-charged` | response, on 200 | "indicates the exact amount that will be billed to your Cloudflare account for the request" |
| `crawler-error` | response, on error | "indicating the specific issue" |
| `cf-pay-per-crawl` | request, to origin only | "indicates the pricing mode in effect", for example `protocol=cloudflare, pricing=in-band` |

- The header is `crawler-price`, not `crawler-prices`. "the `crawler-price` response header is only forwarded to the client when the client is being asked to pay for the content (HTTP 402)" (https://developers.cloudflare.com/ai-crawl-control/features/pay-per-crawl/use-pay-per-crawl-as-site-owner/advanced-configuration/).
- Payment headers "must be included in the `signature-input` header components" of Web Bot Auth.
- Error codes return 402 (`MissingCrawlerPrice`, `InvalidCrawlerExactPrice`, `InvalidCrawlerMaxPrice`), 403 (`CrawlerForbidden`, `PaymentFailed`), 400, 500 or 502 (https://developers.cloudflare.com/ai-crawl-control/features/pay-per-crawl/use-pay-per-crawl-as-ai-owner/error-codes/).
- "Some paths are always free to crawl. These paths are: `/robots.txt`, `/sitemap.xml`, `/security.txt`, `/.well-known/security.txt`, `/crawlers.json`." (FAQ: https://developers.cloudflare.com/ai-crawl-control/features/pay-per-crawl/faq/).
- Order: "AI Crawl Control's AI crawler blocking uses WAF custom rules, which take place before Cloudflare bot solutions" and "pay per crawl takes place after Cloudflare bot solutions" (https://developers.cloudflare.com/ai-crawl-control/configuration/ai-crawl-control-with-bots/).

Does a 402 reach a browser-like or unknown user agent? Cloudflare does not say so directly. Three statements point towards no:

- The `cf-pay-per-crawl` value `bypass` applies "When the request is not subject to payment (for example, not a bot)."
- Owners pick which crawlers to charge from the AI Crawl Control list. "On the free plan, AI Crawl Control identifies AI crawlers based on their user agent strings."
- The FAQ tells operators: "Use the standard user agents associated with your AI crawler that you have onboarded to Cloudflare and identified through Web Bot Auth."

Our inference is that a browser-like or unlisted user agent is not charged and does not get the pricing 402. It may still be blocked or challenged by other rules. This is an inference, not a documented guarantee.

A 402 does not by itself prove Pay Per Crawl. AI Crawl Control lets a paying site owner return "`402 Payment Required`" as a custom block response. Only `crawler-price` tells the two apart.

## 4. Cloudflare Content Signals

Sources: https://contentsignals.org/ (no date) and https://developers.cloudflare.com/bots/additional-configurations/managed-robots-txt/ (last updated Oct 8, 2026).

The syntax on contentsignals.org:

```txt
User-Agent: *
Content-Signal: ai-train=no, search=yes, ai-input=no
Allow: /
```

The line Cloudflare's managed robots.txt writes, with lower-case "signal":

```txt
User-Agent: *
Content-signal: search=yes, ai-train=no, use=reference
Allow: /
```

Signal names and meanings, quoted from the policy comment Cloudflare prepends:

- "search: building a search index and providing search results (e.g., returning hyperlinks and short excerpts from your website's contents). Search does not include providing AI-generated search summaries."
- "ai-input: inputting content into one or more AI models (e.g., retrieval augmented generation, grounding, or other real-time taking of content for generative AI search answers)."
- "ai-train: training or fine-tuning AI models."

Values and defaults:

- The values are `yes` and `no`. "If a content-signal = yes, you may collect content for the corresponding use." "If a content-signal = no, you may not collect content for the corresponding use."
- A missing signal is neutral: "the website operator neither grants nor restricts permission via content signal with respect to the corresponding use."
- Cloudflare is "testing `content-use`", a fourth field with `use=immediate` ("Interact, but store and reuse nothing."), `use=reference` ("Index, excerpt, and link back.") or `use=full` ("Summarize and reproduce."). contentsignals.org does not list it.

Where the line sits:

- Every example places it inside a user-agent group, after a `User-Agent` line, on its own or per bot (`User-Agent: googlebot`, `User-Agent: bingbot`, `User-Agent: OAI-Searchbot`).
- contentsignals.org also shows a path-scoped form: `Content-Signal: /about ai-train=yes, search=yes, ai-input=yes`.
- Neither page states a rule about placement outside a group.
- Signals also travel as an HTTP response header. Markdown for Agents adds `Content-Signal: ai-train=yes, search=yes, ai-input=yes` when the origin sets none (section 7). On 19 October 2026 we saw `content-signal: ai-train=yes, search=yes, ai-input=yes` on Cloudflare's own docs and blog responses.

Who honours the signals:

- contentsignals.org itself: "Not all automated systems honor robots.txt files, and some may ignore these Content-Signal directives."
- None of the vendor crawler pages in section 1 mentions Content-Signal. We searched the OpenAI, Anthropic, Perplexity, Bing, Apple, Mistral, DuckDuckGo, Amazon, Meta, Google and Common Crawl pages for "content-signal" and "content signal" and found no match.
- Google's robots.txt spec: "Google supports the following fields (other fields such as `crawl-delay` aren't supported)", and lists `user-agent`, `allow`, `disallow` and `sitemap` (https://developers.google.com/crawling/docs/robots-txt/robots-txt-spec, last updated 2026-08-31).
- Cloudflare warns that "Google Search Console may occasionally report `Syntax not understood` for Content Signals".
- The only enforcement on record is Cloudflare's own: "setting Training to Disallow adds managed directives and enables edge blocking for AI training crawlers. Mixed-use crawlers are excluded from this edge block."

## 5. IndexNow key discovery

Sources: https://www.indexnow.org/documentation and https://www.indexnow.org/faq (no dates).

How the key file is published:

- "You must host a UTF-8 encoded text key file {your-key}.txt listing the key in the file at the root directory of your website."
- The FAQ example: "if your key is abcd1234, create a file named abcd1234.txt with the contents abcd1234".
- Key format: "Your-key should have a minimum of 8 and a maximum of 128 hexadecimal characters. The key can contain only the following characters: lowercase characters (a-z), uppercase characters (A-Z), numbers (0-9), and dashes (-)." The two sentences disagree. The FAQ drops "hexadecimal".

`keyLocation` lets the file live elsewhere on the same host:

- "You can also host one to many UTF-8 encoded text key files in other locations within the same host and you must tell search engines the location of this text key file in each IndexNow notification by specifying the location using the keyLocation variable."
- It limits scope: "A key file located at http://example.com/catalog/key12457EDd.txt can include any URLs starting with http://example.com/catalog/".
- "It is strongly recommended that you use Option 1 and place your file key at the root directory of your web server."

Can a third party discover the key? No, by design:

- "Only you and the search engines should know the key and your file key location."
- Neither page defines a well-known path, meta tag, robots.txt line or HTTP header for the key. The FAQ example name `https://yourdomain.com/keys/well-known.txt` is a sample non-root location, not a well-known URI.
- The FAQ adds: "When your CMS, hosting provider, or SEO plugin supports IndexNow, you don't need a key file. Submissions are handled automatically."

How platforms publish it:

- Cloudflare Crawler Hints mentions no key file. It "uses cache-status `MISS` to determine when content has likely been updated and sends it to IndexNow's crawler" (https://developers.cloudflare.com/cache/advanced-configuration/crawler-hints/, last updated Aug 14, 2026).
- The IndexNow WordPress plugin, by "bingwebmastertools", version 1.0.4, "Last updated 4 months ago": "Once installed, the plugin will automatically generate and host the API key on your site." No path is given (https://wordpress.org/plugins/indexnow/). The plugin's source browser on plugins.trac.wordpress.org returned 403.
- Rank Math "automatically generates an API key for your website, dynamically hosts it on your website, and serves it to the search engines." A "Check Key" button opens "the location where Rank Math hosts the API key". When that fails, the fix is "manually add the text file to the root of your website with the following name: `[your_api_key].txt`" (https://rankmath.com/kb/how-to-use-indexnow/).
- Yoast's IndexNow is a Premium feature: "we’ll automatically ping the participating search engines whenever you publish, update, or delete a post" (https://yoast.com/help/yoast-seo-settings-site-features/). Its developer page's "Keys & URLs" section reads "Pending" (https://developer.yoast.com/features/integrations/indexnow/).

For the audit: a check that does not know the key cannot confirm from the site that it uses IndexNow. Nothing we fetched documents a public signal. Any proxy, such as spotting a plugin, is our inference and not an IndexNow signal.

## 7. Markdown for agents

### Agents that send `Accept: text/markdown`

- Claude Code documents it: "WebFetch sets a `User-Agent` header beginning with `Claude-User`, and an `Accept` header that prefers Markdown over HTML so servers that support content negotiation can return Markdown directly." (https://code.claude.com/docs/en/tools-reference.md).
- OpenCode's docs page says only "Fetch web content" (https://opencode.ai/docs/tools/). Its source defaults to Markdown and sends `text/markdown;q=1.0, text/x-markdown;q=0.9, text/plain;q=0.8, text/html;q=0.7, */*;q=0.1` (https://github.com/anomalyco/opencode/blob/dev/packages/core/src/tool/plugin/webfetch.ts).
- Cursor: we found no Cursor documentation. A third-party test by Checkly, dated February 19, 2026, recorded Cursor 2.4.28 sending `Accept: text/markdown,text/html;q=0.9,application/xhtml+xml;q=0.8,application/xml;q=0.7,image/webp;q=0.6,*/*;q=0.5`. The same test found that OpenAI Codex, Gemini CLI, GitHub Copilot and Windsurf did not ask for Markdown (https://www.checklyhq.com/blog/state-of-ai-agent-content-negotation/).
- Cloudflare's blog, a vendor talking about other vendors, says: "We already see some of the most popular coding agents today – like Claude Code and OpenCode – send these accept headers" (https://blog.cloudflare.com/markdown-for-agents/, February 12, 2026).

### Whether serving markdown changes what bots do

Fetched on 19 October 2026, for the evidence label of `markdown-alternate`.

- Profound, a vendor that sells AI bot analytics, "Does Markdown increase AI bot traffic?", 17 February 2026 (https://www.tryprofound.com/blog/does-markdown-increase-ai-bot-traffic): "We A/B tested 381 pages across six sites", from "January 19 – February 8, 2026", tracking "crawlers and user-triggered agents from OpenAI, Anthropic, Perplexity, Meta, and DuckAssistBot". "Markdown pages saw ~1 extra median bot visit over three weeks", and "we can't say with confidence that Markdown actually drove more traffic."
- Cloudflare's launch post (https://blog.cloudflare.com/markdown-for-agents/, published 12 February 2026, modified 15 July 2026) shows a screenshot introduced as "Here are the requests that return markdown to OAI-Searchbot, the crawler used by OpenAI to power ChatGPT's search". The text gives no numbers. The feature answers only a request whose `Accept` names `text/markdown`.
- A counter-datum from one site: Dries Buytaert, 5 March 2026, "a month of Cloudflare logs" (https://dri.es/markdown-llms-txt-and-ai-crawlers). OAI-SearchBot made 5 722 requests, 1 300 of them for `.md` files and none with content negotiation. "No AI crawler uses content negotiation. Not one. They only discover the Markdown pages through the dedicated URLs, and only via the auto-discovery link." And: "llms.txt is a solution looking for a problem."

### Cloudflare Markdown for Agents

Source: https://developers.cloudflare.com/fundamentals/reference/markdown-for-agents/ (last updated Oct 9, 2026).

- How it triggers: "the client needs to add the `Accept` negotiation header with `text/markdown` as one of the options."
- Response headers:
  - "`Content-Type` is set to `text/markdown; charset=utf-8`."
  - "`Vary` includes `Accept`".
  - "`Content-Length` is removed because the Markdown response is streamed."
  - "`Content-Encoding`, `Content-Range`, `Transfer-Encoding`, `ETag`, and `Last-Modified`" are removed.
  - When the origin sets no `content-signal`, it "adds a default `Content-Signal: ai-train=yes, search=yes, ai-input=yes`".
- Output: YAML front matter from `title`, `description` and `og:image`, then the body, then JSON-LD "as a fenced `json` code block at the end".
- Limits: "Conversion is limited to 6 MiB (6,291,456 bytes) of decompressed HTML."
- Plans: "Pro, Business and Enterprise plans, and SSL for SaaS customers at no cost".
- The February 2026 blog describes an `x-markdown-tokens` header. The October 2026 docs do not list it. Our live check on 19 October 2026 of blog.cloudflare.com and developers.cloudflare.com with `Accept: text/markdown` returned `content-type: text/markdown; charset=utf-8`, `vary: accept-encoding, accept` and `content-signal: ai-train=yes, search=yes, ai-input=yes`, with no `x-markdown-tokens`.

### Vercel

- Blog, February 3, 2026: "Many agents already send `Accept: text/markdown` when fetching pages". It shows a Next.js rewrite on the `accept` header and route handlers returning `'Content-Type': 'text/markdown'` (https://vercel.com/blog/making-agent-friendly-pages-with-content-negotiation).
- Knowledge base, last updated 2026-09-03: "A request with `Accept: text/markdown` should receive Markdown with `Content-Type: text/markdown; charset=utf-8`. Include `Vary: Accept` so caches keep the HTML and Markdown responses separate. If Markdown is unavailable, return HTML with its correct content type." (https://vercel.com/kb/guide/make-your-site-readable-by-ai-agents).
- Live check on 19 October 2026: `https://vercel.com/docs/bot-management` with `Accept: text/markdown` returned `content-type: text/markdown; charset=utf-8`, `vary: Accept` and `link: <https://vercel.com/docs/bot-management>; rel="canonical"`.

### `<link rel="alternate" type="text/markdown">`

- llmstxt.org v2 documents it: "`rel="alternate" type="text/markdown"` points to the markdown version of a page, and `rel="describedby"` points to the llms.txt file that covers it. … These links can be provided as HTML `<link>` elements, or as an HTTP `Link:` response header." Its example: `Link: </docs/page.html.md>; rel="alternate"; type="text/markdown", </docs/llms.txt>; rel="describedby"`.
- Vercel's knowledge base uses it the same way: `<link rel="alternate" type="text/markdown" href="/docs/quickstart.md">`, and adds that an HTTP `Link` header can carry the same relation.
- Vercel's February blog points the alternate link at llms.txt instead: `<link rel="alternate" type="text/markdown" title="LLM-friendly version" href="/llms.txt" />`. That conflicts with llmstxt.org v2.
- Seen in page HTML on 19 October 2026: Cloudflare docs (`…/index.md`), Perplexity docs (`/docs/resources/perplexity-crawlers.md`) and Vercel docs (`https://vercel.com/docs/bot-management.md`).
- One web search found no formal standard for this convention.

### The `.md` suffix

llmstxt.org v2: pages should "provide a clean markdown version of those pages at the same URL as the original page, either with `.md` appended (`page.html.md`) or with the extension replaced by `.md` (`page.md`). (URLs without file names should append `index.html.md` or `index.md` instead.)"

### llms.txt specification

Source: https://llmstxt.org/ (served as Markdown at https://llmstxt.org/index.md). The page header still reads "2024-09-03". The changes page dates "v2 (August 2026)" (https://llmstxt.org/changes.md).

- Location: "at the root path `/llms.txt` of a website or at any subpath (e.g. `/docs/llms.txt`). A file covers the URLs under its path, and where more than one file applies, agents should use the most specific one."
- Structure, in order:
  - "An optional byte-order mark (BOM)"
  - "An H1 with the name of the project or site. This is the only required section"
  - "A blockquote with a short summary of the project"
  - "Zero or more markdown sections (e.g. paragraphs, lists, etc) of any type except headings"
  - "Zero or more markdown sections delimited by H2 headers, containing “file lists” of URLs", where each item has "a required markdown hyperlink `[name](url)`, then optionally a `:` and notes about the file"
- The "Optional" section is now just a convention: "they no longer carry mechanical semantics".
- Served type: the spec does not name one. On 19 October 2026 llmstxt.org, fastht.ml, developers.cloudflare.com and vercel.com all served their `llms.txt` as `text/plain; charset=utf-8`.
- Chrome Lighthouse checks it: "Lighthouse flags the pages if a server error occurs when attempting to retrieve the `llms.txt` file. If the file is not provided by the server (resulting in a 404), the audit is marked as Not Applicable (N/A)" (https://developer.chrome.com/docs/lighthouse/agentic-browsing/llms-txt, last updated 2026-05-05).
- Google Search ignores it: "You don't need to create new machine readable files, AI text files, markup, or Markdown to appear in Google Search (including its generative AI capabilities), as Google Search itself doesn't use them." (https://developers.google.com/search/docs/fundamentals/ai-optimization-guide, last updated 2026-07-10).

## 8. Bing guidance on page shape for AI answers

Source: Bing Webmaster Guidelines, https://www.bing.com/webmasters/help/webmaster-guidelines-30fba23a (no date on the page). The guidelines say they cover "Bing search experiences, Copilot, and grounding API results".

Section 17, "Focus Each URL on a Single Topic":

- "URLs focused on a primary topic are more likely to be selected for grounding results."
- "Avoid mixing unrelated concepts on a single URL"
- "Align titles, heading, and content intent"

Section 18, "Surface Key information early":

- "Place essential information near the top of the URL"
- "Avoid long introductions before addressing the main topic."
- "Early clarity improves grounding visibility and reliability."

Related sections:

- Section 15: "URLs are more likely to be selected for grounding queries and citations when content stands on its own." "Important information is visible on the URL itself"
- Section 11: content should "Be easy to understand without external context".
- Section 13: "Missing, duplicate, or overly short title tags and meta descriptions may reduce indexing reliability, ranking, and eligibility for grounding results and citations."
- The abuse list: "GEO does not guarantee grounding or citations in AI experiences."

Microsoft Advertising blog, "Optimizing your content for inclusion in AI search answers", October 08, 2025 (https://about.ads.microsoft.com/en/blog/post/october-2025/optimizing-your-content-for-inclusion-in-ai-search-answers):

- "Assistants like Copilot break content down, a process called parsing, into smaller, structured pieces that can be evaluated for authority and relevance."
- "Your page title, description, and H1 tag (the top-level HTML heading) are important signals AI systems use to interpret purpose and scope."

Google takes the opposite line on chunking: "There's no requirement to break your content into tiny pieces for AI to better understand it. Google systems are able to understand the nuance of multiple topics on a page and show the relevant piece to users." (Google AI optimisation guide above).

## 9. Spoofed bot user agents and the CDN test

The planned CDN test sends each AI search agent's user agent from Citequill's own Vercel (AWS) addresses, with no bypass secret. A CDN that verifies bots by IP sees a fake bot. We checked which defaults block or challenge such a request, and whether the response shows why. All pages were fetched on 19 October 2026. Our own inferences are labelled as such.

### Cloudflare settings that act on a spoofed bot

#### Fake bot rules in the Cloudflare Managed Ruleset

Source: https://developers.cloudflare.com/waf/troubleshooting/fake-bot-managed-rules/ (last updated May 5, 2026).

- How they work: "These rules compare the request's `User-Agent` header against known bot patterns and then verify the source using methods like reverse DNS lookup or IP validation. If the `User-Agent` matches a known bot but the source cannot be verified, the rule flags the request as a fake bot."
- The page lists two rules only: `Anomaly:Header:User-Agent - Fake Google Bot` and `Anomaly:Header:User-Agent - Fake Bing or MSN Bot`. No page we fetched lists a fake-bot rule for Applebot, OAI-SearchBot, Claude-SearchBot, PerplexityBot, MistralAI-Index, DuckAssistBot, Amzn-SearchBot or meta-webindexer. The WAF changelog pages for 2022, 2023, 2024 and the current year name no other fake-bot rule.
- The Google rule has been off since 10 February 2026: "This week’s release changes the rule action from BLOCK to Disabled for Anomaly:Header:User-Agent - Fake Google Bot." (https://developers.cloudflare.com/changelog/post/2026-02-10-waf-release/, February 10, 2026).
- No page gives the Bing rule's action in a table. The only statement is on the Bing Site Scan page, which calls it "the WAF managed rule that blocks fake Bingbot requests" and tells owners to "delete the exception to start blocking fake Bingbot requests again" (https://developers.cloudflare.com/waf/troubleshooting/blocked-bing-site-scans/, last updated May 5, 2026).
- The troubleshooting page names a case like ours: "Third-party uptime monitors or automated testing tools that set a bot-like `User-Agent` header may also be flagged."

#### Plans and default deployment of the fake bot rules

- The Free plan does not have the Cloudflare Managed Ruleset. The availability table row reads "Cloudflare Managed Ruleset | No | Yes | Yes | Yes" for Free, Pro, Business and Enterprise (https://developers.cloudflare.com/waf/managed-rules/, last updated Sep 8, 2026).
- On Pro and above, the owner deploys it. The getting-started guide's first step ends "Turn on Cloudflare managed ruleset" (https://developers.cloudflare.com/waf/get-started/, last updated Aug 3, 2026). No page we fetched says it is on by default for a new Pro or Business zone.
- Once deployed, only some rules run: "By default, the Cloudflare Managed Ruleset enables only a subset of rules" (same guide). The Bing Site Scan page implies the Bing rule is in that subset. No page lists the subset.
- Free plans get the Free Managed Ruleset instead: "The Free Managed Ruleset is deployed by default on Free plans" (same guide). Cloudflare does not publish its rules. The reference URL `/waf/managed-rules/reference/cloudflare-free-managed-ruleset/` returned 404, and the full WAF documentation text names no rule in it. We cannot tell whether it includes the Bing rule.

#### Browser Integrity Check

Source: https://developers.cloudflare.com/waf/tools/browser-integrity-check/ (last updated Aug 3, 2026).

- "Browser Integrity Check is enabled by default." It is the one default-on Cloudflare check we found that reads the user agent.
- It "looks for common HTTP headers abused most commonly by spammers and denies access to your page." It "also challenges visitors without a user agent or with a non-standard user agent such as commonly used by abusive bots, crawlers, or visitors."
- Its block shows as Error 1010, "The owner of this website has banned your access based on your browser's signature", and the fix is to "turn off Browser Integrity Check" (https://developers.cloudflare.com/support/troubleshooting/http-status-codes/cloudflare-1xxx-errors/error-1010/, last updated Apr 23, 2026).
- The page does not say whether a verified bot's user agent from a wrong IP counts as non-standard, or whether verified bots skip the check.

#### Bot Fight Mode

- It is a Free plan feature that the owner switches on. The setup steps say "Turn Bot fight mode on" (https://developers.cloudflare.com/bots/get-started/bot-fight-mode/, last updated Aug 3, 2026). The docs do not say it is on by default.
- It targets "Simple bots from cloud hosting providers and headless browsers", and its action is "Cloudflare issues a computationally expensive challenge" (https://developers.cloudflare.com/bots/plans/free/, last updated May 6, 2026).
- "You cannot bypass or skip Bot Fight Mode using WAF custom rules or Page Rules." (Bot Fight Mode page).
- Real verified bots are left alone: "Historically, Verified bots have been excluded in default bot configurations across all plans." (https://developers.cloudflare.com/bots/concepts/bot/verified-bots/, last updated Oct 8, 2026).
- The docs say nothing about spoofed verified bots. Our inference: Citequill's AWS addresses belong to a cloud hosting provider, so Bot Fight Mode would challenge Citequill whatever user agent it sends, while the real agent passes as a verified bot. Without a control request, every agent would show a false block.

#### Super Bot Fight Mode and bot score

- Super Bot Fight Mode is on Pro, Business and Enterprise without Bot Management, and the owner turns it on: "Turn Super Bot fight mode on" (https://developers.cloudflare.com/bots/get-started/super-bot-fight-mode/, last updated Aug 3, 2026).
- Its groupings: "Definitely automated" "Blocks or challenges traffic with a bot score of 1" (Pro and up), "Likely automated" "Blocks or challenges traffic with a bot score of 2-29" (Business and up), and "Verified bots" (https://developers.cloudflare.com/bots/additional-configurations/custom-rules/, last updated Apr 15, 2026).
- A spoofed request cannot be in the Verified bots grouping. A bot is verified only when "it declares who it is deterministically, through a cryptographic Web Bot Auth signature, a published IP list with a stable user-agent, or reverse DNS" (https://developers.cloudflare.com/bots/concepts/bot/verified-bots/, last updated Oct 8, 2026).
- "Granular bot scores are only available to Enterprise customers who have purchased Bot Management." (https://developers.cloudflare.com/bots/concepts/bot-score/, last updated Aug 26, 2026).
- No page states what score or grouping a spoofed verified bot gets. No page gives the default action of each grouping when Super Bot Fight Mode is first turned on.

#### AI Crawl Control and the AI bot presets

- Below Enterprise, AI Crawl Control matches by user agent. Its plan table sets "AI crawler detection via user agent strings" for "All plans" against "Advanced AI crawler detection via Bot Management detection ID" for "Enterprise plans with Bot Management" (https://developers.cloudflare.com/ai-crawl-control/get-started/, last updated Apr 23, 2026).
- The Manage AI crawlers page words it as a Free plan limit: "On the free plan, AI Crawl Control identifies AI crawlers based on their user agent strings." It adds: "Upgrade your plan to enable a more thorough detection using Cloudflare's Bot Management detection ID field." (https://developers.cloudflare.com/ai-crawl-control/features/manage-ai-crawlers/, last updated Jul 28, 2026). Detection IDs need Bot Management, an Enterprise add-on, so in effect Free, Pro and Business all match by user agent.
- The GraphQL reference marks the user agent filter "Can be spoofed" and the detection ID filter "Reliably verified by Cloudflare" (https://developers.cloudflare.com/ai-crawl-control/reference/graphql-api/, last updated Apr 23, 2026).
- A block is "one WAF custom rule". "If you choose to allow all AI crawlers, AI Crawl Control does not utilize any WAF custom rules." (https://developers.cloudflare.com/ai-crawl-control/configuration/ai-crawl-control-with-waf/, last updated Aug 3, 2026).
- Our inference: on Free, Pro and Business, AI Crawl Control blocks a spoofed request exactly when it blocks the real agent. For this feature the CDN test gives a true finding.
- The Search, Agent and Training presets say: "Each blocking option will block Verified bots classified with that behavior, plus additional unverified bots that fall under these classifications." (https://developers.cloudflare.com/bots/additional-configurations/block-ai-bots/, last updated Jul 1, 2026). The page does not say how it treats an unverified request that names a verified bot.

#### Web Bot Auth

- "Web Bot Auth is an authentication method that leverages cryptographic signatures in HTTP messages to verify that a request comes from an automated bot." (https://developers.cloudflare.com/bots/reference/bot-verification/web-bot-auth/, last updated Oct 8, 2026).
- It is one route to verified status. The page documents no action against a request that carries no signature.

### What a Cloudflare block tells the client

- Managed and custom WAF rules share one block response. "Requests blocked by WAF custom rules or WAF managed rules do not get a 1020 error. These requests get the WAF block response instead." (https://developers.cloudflare.com/support/troubleshooting/http-status-codes/cloudflare-1xxx-errors/error-1020/, last updated Oct 14, 2026).
- "The default block response is a Cloudflare standard HTML page." (https://developers.cloudflare.com/waf/reference/legacy/firewall-rules-upgrade/). The error page types table: "WAF block | The page displayed when visitors are blocked by a Web Application Firewall rule. This page returns a `403` status code." (https://developers.cloudflare.com/rules/custom-errors/reference/error-page-types/, last updated Apr 16, 2026).
- AI Crawl Control blocks are WAF custom rules (section 2). Fake-bot blocks are WAF managed rules. Both get the same WAF block page and 403 unless the owner set a custom response, so neither the status nor the page type tells them apart.
- Error 1020 "Access denied" now comes from other features. Its cause: "A security rule with a Block action matched the request, and the rule has no custom response configured." The page's examples are API Shield schema validation and JWT validation (1020 page).
- Error 1010 marks Browser Integrity Check (above).
- Challenges: "Managed challenge / I'm Under Attack Mode … This page returns a `403` status code." (error page types table). With section 2, a challenge is a 403 that carries `cf-mitigated: challenge`.
- Cloudflare-generated error pages carry `cf-error-type` and `cf-error-origin` (https://developers.cloudflare.com/support/troubleshooting/http-status-codes/cloudflare-error-headers/, last updated Apr 23, 2026). The listed values are `1000`, `1016`, `1101`, `1102` and `52x`. The page does not say whether a WAF block page carries them, or which `cf-error-origin` value the WAF sets.
- The default block page's wording, such as "Sorry, you have been blocked", appears on no page we fetched.
- Bot Fight Mode and Super Bot Fight Mode responses are not documented beyond "challenge" and "block". The product that acted is named only in the owner's dashboard: "Any requests challenged by this product will be labeled Bot Fight Mode in the Service field." (Bot Fight Mode page).
- The owner finds the rule from the Ray ID: "Search the Security Events log … for the Ray ID or client IP address from the visitor's 1020 error message. The event shows which security feature and rule blocked the request." (1020 page).
- Our inference: from the client side, a Cloudflare 403 shows that Cloudflare blocked or challenged the request, not which rule did. A client cannot tell an AI Crawl Control block from a fake-bot block unless the owner set a custom AI Crawl Control response.

### Vercel and spoofed bots

How Vercel verifies:

- "To prove that bots are legitimate and verify their claimed identity, several methods are used". The page lists "IP Address Verification", "Reverse DNS Lookup" and "Cryptographic Verification" through Web Bot Auth (https://vercel.com/docs/bot-management, last updated 2026-09-10).
- Changelog, August 12, 2025: bots in the directory "are verified by IP, reverse DNS, and now Web Bot Auth", so that legitimate automation gets through "while spoofed bots are blocked". The sentence sits in a post about Bot Protection (https://vercel.com/changelog/vercels-bot-verification-now-supports-web-bot-auth).
- Changelog, September 30, 2025: Observability gained "Bot verified: Distinguish between verified, spoofed, and unverifiable bots" (https://vercel.com/changelog/view-and-query-bot-verification-data-in-vercel-observability). Vercel classifies a spoofed bot apart from an unknown one. No page says whether any action differs.
- Changelog, June 5, 2025: "Bot Protection complements Vercel's existing mitigations, which already block common threats like DDoS attacks, low quality traffic, and spoofed traffic." (https://vercel.com/changelog/bot-protection-is-now-generally-available). The post does not define "spoofed traffic". No docs page describes an always-on block of spoofed bots.

Rulesets and modes:

- Bot Protection: "The ruleset is inactive by default." In challenge mode it "will serve a JavaScript challenge to traffic that is unlikely to be a browser". It "prevents requests that falsely claim to be from a browser such as a `curl` request identifying as Chrome" and "automatically excludes verified bots" (bot management page and https://vercel.com/docs/vercel-firewall/vercel-waf/managed-rulesets).
- Our inference: when Bot Protection is on, it challenges a spoofed bot and a neutral control alike, because neither is verified and neither is a browser. The OAI-SearchBot, Bingbot and Applebot strings embed a browser version (section 1), which may count as falsely claiming a browser.
- AI bots ruleset: "The ruleset is inactive by default." It "identifies and filters requests from known AI crawlers and bots". The docs do not say whether it matches by user agent or by verification.
- Attack Mode: "Attack Mode automatically recognizes and allows these bots to pass through without being challenged." Only the site's own account is exempt: "Other Vercel accounts cannot bypass Attack Mode on your projects." (https://vercel.com/docs/vercel-firewall/attack-mode). Our inference: a spoofed bot from Citequill's account is challenged like any other client.
- Custom rule parameters include User Agent, IP Address, AS Number and JA3 and JA4 digests. None is a verified-bot condition (https://vercel.com/docs/vercel-firewall/vercel-waf/rule-configuration, last updated 2025-04-21). An owner's rule on a bot's user agent therefore hits real and spoofed requests alike.

### Telling a site block from a spoofed-bot block

- No vendor page we fetched documents a method for a third-party checker. Cloudflare's fix for a fake-bot false positive is on the owner's side: "create an exception to skip the specific managed rule for the affected requests" (fake bot page).
- Cloudflare Radar's URL Scanner accepts a custom user agent, `"customagent": "XXX-my-user-agent"` (https://developers.cloudflare.com/radar/investigate/url-scanner/, last updated Apr 20, 2026). The page says nothing about testing bot blocks or about spoofed bots.
- Third-party: 365i's AI Crawler Checker sends a baseline and a control (https://www.365i.co.uk/tools/ai-bot-checker/, no date). "We fetch your homepage once as a normal browser, then once as each bot, and compare." Then "we send one more request as our control bot: a crawler no host has ever written a rule for. If it gets through and GPTBot does not, a rule is targeting GPTBot by name. If it is refused too, your host filters unrecognised bots as a class."
- The same page admits the false positive this section is about: "Our test requests come from our own servers, not from OpenAI's or Anthropic's networks. Some security systems verify crawlers by IP address and only reject impostors while letting the real, verified bot through. From the outside those two cases look identical." It leaves the owner to ask the host whether "the genuine crawler, coming from the provider's published IP ranges" is allowed.

Our inference:

- A browser baseline and a neutral bot control separate three causes: everything from Citequill's address is blocked (Bot Fight Mode, Attack Mode, DataDome, the AWS data center signal), every non-browser client is blocked (Browser Integrity Check, Vercel Bot Protection, Sucuri's aggressive filter), or only the named agent is blocked.
- No control separates "the site blocks Bingbot by name" from "the fake Bingbot rule fired". Both rules key on the same name, both let the control through, and both return the same WAF block page.
- A neutral bot-like control can itself be challenged by Browser Integrity Check as a "non-standard user agent", so the browser baseline is needed as well.
- The CDN test can honestly report "the CDN refuses this user agent from our address". That matches what the real agent meets where the CDN does not verify by IP, as with AI Crawl Control below Enterprise. It may not match for Bingbot on a Cloudflare zone with the Managed Ruleset on, for any agent behind DataDome or a Fastly impostor rule, or for agents that AWS Bot Control classes as search engines. AWS blocks its AI category whether the bot is verified or not, so there the finding holds. AWS does not publish which agent sits in which category.

## What contradicts an audit's likely assumptions

- Anthropic documents no full user agent string for ClaudeBot, Claude-SearchBot or Claude-User. Only Claude Code's docs say WebFetch's string begins with `Claude-User`.
- Claude-User honours robots.txt by Anthropic's account. ChatGPT-User ("may not apply"), Perplexity-User ("generally ignores"), Amzn-User ("may not follow all"), Meta-ExternalFetcher ("may bypass") and Google's user-triggered fetchers, including Google-Agent ("generally ignore"), do not promise to.
- Mistral's page does not say MistralAI-Index or MistralAI-User obeys robots.txt. Only MistralAI-Training is tied to a robots.txt disallow.
- Fallback rules change what a robots.txt means. Applebot follows Googlebot rules when Applebot is not named. Amzn-SearchBot follows the rules for "other search bots" when it is not named.
- Meta prints its user agents with a relative link, `(+/documentation/sharing/webmasters/web-crawlers)`. Its robots.txt example does not include `meta-webindexer`.
- Google renamed `Google-NotebookLM` to `Google-GeminiNotebook`; the old value was "supported until August 2026". Google added `Google-Agent` in March 2026.
- `x-vercel-mitigated` is not a documented Vercel header. It shows up only in community reports, with the values `challenge` and `deny`.
- Cloudflare documents `cf-mitigated: challenge` but no status code for challenges, and no header at all for a plain block. The 403 comes from Cloudflare's general 403 page, not from the challenge docs.
- A 402 is not proof of Pay Per Crawl. Cloudflare site owners can return 402 as a custom AI Crawl Control block response. Only `crawler-price` marks Pay Per Crawl.
- Since 15 September 2026, Cloudflare's Block and "Block on pages with ads" also hit Googlebot, Bingbot and Applebot. Cloudflare's own docs page still describes the new-domain default differently from its blog.
- Content Signals have no documented honouring crawler apart from Cloudflare's own edge. Google's robots.txt parser supports four fields only. Cloudflare writes `Content-signal` and contentsignals.org writes `Content-Signal`. The signals also appear as a `content-signal` HTTP header that Markdown for Agents adds by default with every value set to `yes`.
- An IndexNow key cannot be discovered without knowing it: "Only you and the search engines should know the key and your file key location." Crawler Hints and the WordPress plugins publish no documented public marker.
- `noarchive` has opposite weight at Google and Bing. Google ignores it. At Bing it removes the page from Copilot links and from training. Amazon reads it as "do not use the page for model training".
- Bing's guidelines name a `data-snippet` attribute that Bing's robots meta page does not list.
- Google's Search generative AI control is set in Search Console, defaults to Include, and leaves no trace on the page.
- Cloudflare's `x-markdown-tokens` header appears in its February 2026 blog but not in its October 2026 docs, and was absent from the live responses we checked.
- llms.txt v2 makes the H1 the only required part, and its spec names no content type. Real files are served as `text/plain`. Google says Search ignores llms.txt.
- Bing tells sites to focus each URL on one topic and put essential information near the top. Google says chunking is not required and its systems handle several topics on a page.
- On Cloudflare a spoofed AI search agent mostly meets what the real one meets. The documented fake-bot rules cover Googlebot and Bingbot only, and the Googlebot rule has been disabled since 10 February 2026. The Managed Ruleset that holds them is absent on Free and must be turned on by the owner on Pro and up. AI Crawl Control matches by user agent on every plan below Enterprise. Bingbot is the documented exception.
- Elsewhere a block from our address may not be what the real agent meets, and the response does not say. DataDome blocks unauthenticated bots by default, AWS Bot Control blocks unverified search engine bots and data center traffic, and Vercel claims its platform blocks "spoofed traffic". Cloudflare returns the same 403 WAF block page for a fake-bot rule, an AI Crawl Control block and any custom rule. A neutral control request cannot tell a block by name from a fake-bot block.
