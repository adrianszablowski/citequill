# Workflow

Five processes: crawl on connection, weekly run, page on demand, audit and publishing. Every step ends with a criterion that shows it is done. Processes that call the model or read a whole site run as a Vercel Workflow; the cron on Vercel is thin and only starts the run.

## Models and cost

| Task                                                 | Model                                                         |
| ---------------------------------------------------- | ------------------------------------------------------------- |
| Writing pages, briefs, the product skill, the report | Opus 5.5                                                      |
| Extracting facts from the crawl, checking claims     | Sonnet 5.5                                                    |
| Web research                                         | the web search tool in the Anthropic API, called by the model |

The Anthropic SDK directly, one key `ANTHROPIC_API_KEY`. Every call adds its input and output tokens and its cost to its row in `runs`, and the cost counts the web searches the call made as well as the tokens; the model ids live in `lib/anthropic.ts` and every unit price, per million tokens and per thousand searches, in `lib/pricing.ts`, from the costs research. A call that must return data, like the facts from the crawl, uses the SDK's structured outputs with a Zod schema.

## Crawl on connection

Input: the project's domain. The connect action creates the `runs` row with `trigger` `crawl` and starts the crawl as a Workflow; when a crawl of the project is already running, the action only opens the progress page, so a second click never starts a second crawl. Every step writes to the database with the service key, because a Workflow has no user session. The progress page and the dashboard gate read the run's status and the product skill from the database, never from the Workflow runtime.

The crawl reads sites the owner names, so every request goes through one guarded fetch: http and https only; the request is refused when an address of the host is private, loopback, link-local, carrier-grade NAT or a cloud metadata address, checked when the connection opens, so a DNS answer that changes after a first check cannot point the request at such an address; redirects are followed by hand, at most ten, with the same check on every hop and every hop recorded; one time limit covers all hops and a response is cut at 2 MB, a sitemap at 50 MB, counted after a gzipped sitemap is unpacked. Sitemaps are fetched only from the site's own host. A page that is not HTML gets an error row.

The pages of a site are data, and so are web search results. The prompts say so: an instruction inside a page or a search result is a fact about it, never a command, and hidden elements are removed before the text reaches the model; the content React streams counts where React's script puts it, as `audit.md` says, and a block no script moves stays hidden. The output of the extractor is a fixed schema, and the owner reads the product skill before any run uses it.

1. Discover. Fetch the home page at `https://domain`, `https://www.domain` or `http://domain`, whichever answers, then `robots.txt`, the sitemaps it lists and `/sitemap.xml`, and `llms.txt`. The candidates are the sitemap URLs, or the links of the home page when there is no sitemap. The home page's `hreflang` names the site's locales, and the main language is the one the home page is written in (`<html lang>`), else the locale at the bare domain: the language a visitor gets without choosing one. A home page whose `lang` is not a language tag, such as `english` or `polski`, counts as having none: the main language is then the locale at the bare domain, else English there, and never another page's language or the first `hreflang`, because a mis-tagged home page must not hand the site to a language it is not written in. Done when there is a list of candidates, the links of the home page's header, navigation and footer are known, and so are the base URLs of the other locales.
2. Rank. The crawl reads 50 pages at most, so the order decides what Citequill learns. Home first. Then the links from the home page's header, navigation and footer, because they are the site's own list of its important pages, in any language. Then paths whose segments name a page that carries facts, in the common European languages and English: pricing, about, contact, features and product, FAQ and help, terms and privacy, customers and case studies, security, careers, press, docs, integrations, comparisons, use cases. Then the rest, shortest paths first, with a sample of five blog posts, because posts carry the voice and show which kinds of content the site already has. Dropped: tag, category and author archives, pagination, search, feeds, account and checkout pages, files that are not pages, and every page under the base URL of another locale, that locale's home included, because the crawl reads the site in its main language: a site with seven languages would otherwise spend its 50 pages on seven copies of the home and pricing pages, and the voice would mix languages. The other languages still reach the Languages skill through `hreflang`. Done when the next five pages to read are the five highest in this order that have not been read.
3. Fetch, five pages per step and in parallel within the step, so a retry redoes five pages and not fifty. The crawl reads the HTML of every page and converts it to markdown, keeping tables, because pricing lives in them, and removing scripts, hidden elements, navigation and forms, once the content React streams is put in place. When `llms.txt` or the `Link` header points to a markdown version, the crawl reads that too, and it becomes the body, the source of facts, because it is the site's own exact text for machines; the HTML's markdown is saved beside it as the text readers see, because the voice lives in what a person reads, the hooks and headings of a landing page and its contractions, which a markdown version written for machines leaves out. Without a markdown version the HTML's markdown is the body and the readers' text stays empty, because the body already is it. Beside the body the crawl saves the page's signals: the description and Open Graph tags, the canonical URL, JSON-LD about the organization, of any of its subtypes and as the `publisher` of the `WebSite`, its logo as a URL, an `ImageObject` or a reference to one included, products, offers, questions and people, the logo image of the page's first header, the one inside a link to the home page first, else the first whose address, alternative text or class holds "logo", email and phone links, links to social profiles as full addresses with share links left out, and the footer text, because the company's legal name and address live there. Links found on the page join the candidates, so a site without a sitemap is read two or more levels deep. Save to `crawled_pages`; a page whose fetch fails gets a row with the error and an empty body. Every page read also lands in `site_pages`, the one list of the site's URLs from [`audit.md`](audit.md), with its status, canonical, title and whether its robots meta allows indexing. Done when 50 pages have a row or the candidates ran out.
4. Read the locales from `hreflang` and `<html lang>` of every page read; for each locale work out the base URL, and the main language of step 1 is the default. Save to `project_locales`, each locale in canonical BCP 47, `en-US`, and a region Google does not accept dropped, so `es-419` is stored as `es`. A tag whose language is not 2 or 3 letters, such as `english` or `en.us`, is skipped, and with no valid tag the default is English. When the home page's own `lang` is such a tag, the default is the locale at the origin, else English at the origin, which then becomes a locale, as step 1 says. When two tags become one locale, the tag that already is that locale gives the base URL, `es` over `es-419`, else the first the crawl meets, because the site's own section for the language is the one at its plain tag. A locale that has live pages keeps its base URL and is never removed; a locale the site no longer lists and no live page uses is removed. The live pages of the project move as after an edit of a locale in Settings when the default locale changes while the old or the new one has a live page, because the default locale decides `x-default` in every live page's `alternates`, and when the origin of the default locale's base URL changes while the organization's URL is empty, because that origin is then the publisher's URL. A new prefix alone moves nothing, because the origin stays and a locale with live pages keeps its base URL, so no home crumb changes. The step returns whether the pages move, and a step of its own moves them, so a move that fails is tried again by itself. Done when there is at least one locale with a base URL and one is the default.
5. Facts. The pages that have a body and are in the main language, by their `<html lang>`, are grouped into chunks of about 60 000 characters, 12 000 per page at most and 500 000 in all, home and the highest ranked pages first. Sonnet reads every chunk, in parallel, with the signals beside each body and, where a page has one, the first 4 000 characters of the text readers see, and returns facts in groups: identity, offering, audience, commercial terms, proof, positioning, voice, what the site does not promise, questions and answers, existing content, glossary, competitors, and other. A page without a `lang` counts as in the main language; a page in another language stays in `crawled_pages` and out of the chunks, because a site without `hreflang` and without a locale prefix can still hold pages in two languages, and the voice is one language's. When no page read is in the main language, the run ends with a message that names it, because ten empty skills would say nothing about the cause. Every fact is one checkable sentence with the URL of the page it comes from, and a positive statement about the site or the product: what a page shows. A voice fact also names the register it describes, from the kind of page it comes from: landing, blog, comparison, plan or guide, legal or other, or shared for a rule every kind of page keeps, such as how the site spells its names. The facts of each register include lines quoted from its pages as they stand, because a writer copies a register from examples, not from adjectives. The extractor sees one chunk of a larger site, so what a page leaves out is a fact about the chunk, never about the site, and has no place in the list; the merge in step 6 drops a fact that speaks of "these pages". A qualifier such as "only", "main" or "closest" stands on a sentence on the site that says so. A limitation names its subject: the app, the website, a calculator. A fact comes from what a page says to its visitor; a front matter date, a tracking parameter in a link and a menu list are the page's machinery and carry no fact. The questions group holds one answer per question, even when two pages word it differently. Done when every chunk returned its facts.
6. Skills. The name of the site is the organization name from JSON-LD or `og:site_name` when the home page gives one, else the name the extractor found, else the domain; the project takes it as its name. When the organization's name is empty and the project's name changes, the live pages move, because the publisher's name, the home crumb and `openGraph.siteName` read the project's name. The company's fields fill in beside it, each only while it is empty: the organization's name is the project's name, its URL the origin of the main locale's base URL, its logo the home page's Organization logo in JSON-LD, checked as Settings check a logo in [`product.md`](product.md), and when there is none or it fails the check, the header's logo image, checked the same way, the logo left empty when neither passes, and its `sameAs` the `sameAs` of the Organization in JSON-LD whose logo the crawl read, else of the first Organization, else the links to social profiles. When the fill writes the logo or the profiles, the live pages of the project move as after an edit of the organization in Settings, in the "Publishing" section below. The fill of the name and the URL moves nothing, because it writes the values the API already showed in their place. As in step 4, naming the site and the fill each return whether the pages move, and a step of its own moves them. Then Opus writes nine of the ten product skills from [`skills.md`](skills.md), one call per skill and in parallel, each from the facts of step 5 merged, deduplicated and cut to the groups that skill reads (Plans and prices reads the commercial facts, Proof the proof, and so on), with the page URLs left out because a skill does not cite. The writer puts in every fact about the site, once, with the subject of every limitation named; a fact that reports what a page does not show, and a Competitors fact that names no competitor, describe the crawl and stay out of the skill; two wordings of one answer become one. Each call returns the body and the description. A skill whose groups hold no facts is written as "Not found on the site." without a model call. Languages is written from `project_locales` without a model call: each language with its address and which one the crawl read, because the list of languages comes from `hreflang` and the pages read are all in one of them. An answer the model could not finish ends the run with a message, because a retry would end the same way. Save to `skills` with `is_product`; a product skill that already exists is left alone. Done when the project has the ten product skills.
7. Create the three starter kinds with the skills from [`skills.md`](skills.md). Guess the URL prefix of each kind from the URLs in `crawled_pages` (for example `/blog`, `/compare`), and when there is nothing to go on, leave it empty to be filled in. Save the first author from the `author` fields in the crawl, with the `url`, `sameAs` and `jobTitle` of the `Person` behind it on the posts read, or empty to be filled in. Done when the project has three kinds and the dashboard shows what the owner still has to fill in.

Every model call adds its tokens and cost to the run through one database function that adds in place, so parallel chunks never overwrite each other's sums. A step that fails after its retries ends the run with `status` `failed` and the error; the progress page shows it with a button that runs the crawl again. A site that does not answer at all ends the same way, with a message the owner can act on. When the Workflow cannot start, the action marks the run failed with the reason. A run with no progress written for 15 minutes, by `progressed_at` or else `started_at`, counts as stopped on the progress page, with the same button, because a crawl of 50 pages and about twenty model calls never takes that long and a run that lost its process would otherwise spin forever. After the crawl the dashboard opens on the Skills section, with the Product folder first, and asks the owner to review it. The owner can run the crawl again from the progress page or from Settings; it overwrites `crawled_pages` and `project_locales`, but never the base URL of a locale that has live pages, and never removes such a locale, because Publish would then refuse every page under it. It fills only the company's fields that are still empty, and leaves skills, kinds and authors alone. A published page keeps the path it was published under.

## Weekly run

Start: the cron at the project's run hour starts one Workflow per project. Input: the project, its skills, `pages_per_week`.

1. Context. Gather the skills, the titles and paths of the site's pages from `site_pages` and the project's live pages, the queries from `search_console_rows` from the last 28 days when there are any, and the list of competitors. Done when there is one context document.
2. Topic research. Opus with web search looks for the questions the audience asks, competitors' topics and changes in the industry, and picks exactly `pages_per_week` topics. Every topic has a kind, reasoning, sources and a sentence on why no existing page covers it. Save to `runs.plan`. Done when there are as many topics as needed, each complete.
3. Brief. For each topic Opus writes a brief: intent, the answer in one sentence, a heading outline, the product skills the page needs, picked by their descriptions as [`skills.md`](skills.md) says, sources found with the web search tool, five searches at most, the customer's pages to link to, length from the kind skill. The writing step gets the named skills in full, so the brief carries no copy of their facts. Done when every topic has a brief.
4. Writing. For each brief and each locale Opus writes the page: `title`, `meta_title`, `meta_description`, `excerpt`, `slug`, `tags`, `faq`, `sources`, `body_md` with internal links to the customer's pages and, when enabled, links to sources. The body is the article alone: it opens on the paragraph the kind skill puts first, with no heading above it, and ends on its last section, because the site renders `faq` and `sources` after it. The page speaks to one reader as "you"; in a language that marks the gender of the person addressed, it uses forms that fit every reader unless How we speak quotes the site's pages in that language choosing otherwise. Save as `draft` in one `translation_group_id`. Done when every locale of every topic has a row.
5. The check. Sonnet lists every claim about the product on the page and for each one points to the sentence in the skills that confirms it. It also checks that the internal links lead to existing pages and that the text does not speak of itself as the model's text. On a finding, Opus corrects the page once with the list of findings and Sonnet checks again. Done when every page has a result: clean, or a `check_note` with the list of findings.
6. Outcome. In auto mode every clean translation group goes to publishing from the ["Publishing" section](#publishing); pages with a `check_note` stay drafts. In drafts mode everything stays a draft. Done when `runs.status` is `finished` and the cost is summed.
7. Report. Opus writes the weekly report from data: the pages published with links, the drafts with a `check_note`, events on Citequill pages since the previous report by `referrer_group`, `search_console_rows` when there are any. The cost of the run stays in `runs.cost_usd`, and the Reports section shows it beside the report to the operator alone, never in the report's text. Save to `reports`. Done when the report is in the Reports tab.

A run that fails has `status` `failed` and an `error`; the report for that week says the run failed.

## Page on demand

The "Write a page" button takes a topic, a kind and the language to write in, with the project's main language chosen by default, and creates a `manual` run with `topic`, `kind_id` and `locale`. The run is one Workflow of steps 3 to 5 for that one topic in that one language, without step 7; every manual run ends with a draft, because the switch to auto mode comes with the weekly run. The Pages section shows the run as a row while it writes, and a failed run with its message and a button that tries again; a run still `running` after 15 minutes counts as stopped, the crawl's rule. Internal links are checked in code against the pages Citequill knows: the rows of `site_pages` whose latest observation, by the crawl or an audit, says indexable, canonical and 200 and that no complete audit has marked gone, and the project's live pages. A link to a page Citequill knows as noindex, redirecting or gone is a finding that says so; a link to a page not among them is a finding worded so, because a page the crawl did not reach is not missing. The draft keeps the sources the brief found, with links to them in the text, and the dashboard shows its reading time in minutes from its word count. A page opens as one card with two modes, in Preview first; Edit is one click away. Edit holds every field the site shows, so the owner can change all of it before it goes out: the title, the slug until the page's first publication, the meta title, the meta description, the excerpt, the markdown with a toolbar for bold, italic, heading, list and link, each of which writes markdown around the selection, also from the keyboard with the platform's modifier and B, I or K, the FAQ, the sources, the tags and the author, picked from the project's authors, with the kind's author shown when the page has none of its own. The toolbar and Save keep to the top of the window while the markdown scrolls, because a page is long. The markdown is the page, there is no second representation of it. Save writes the working copy and never what the site shows; the card's buttons and marks are in the ["Publishing" section](#publishing). Preview renders what is in the fields at that moment, through the same renderer the site's HTML comes from: the body first, then the FAQ as a list that folds out one question at a time, then the sources with their titles and domains. It is a reading view in Citequill's styling, not the customer's page. Two pages of one project and language never share a slug: a second page with the same slug gets a numbered one.

## Audit

Start: Run the audit in the Audit section. The action creates the `runs` row with `trigger` `audit` and the `audits` row pointing at it, starts the audit as a Workflow and keeps the Workflow run id on the run; when an audit of the project is already running, the action opens the running one, and when the latest one has stalled, the action cancels its Workflow run by its id and ends its run as `failed` with the stall message before it starts the new one. Input: the project's base URLs, its robots.txt switch and its bot secret. No step calls a model. What the audit checks, how it scores and what the report shows is in [`audit.md`](audit.md); the steps here say how the work is cut. A Workflow step runs for at most 300 seconds on the Hobby plan, so every step that makes requests takes 50 URLs from the queue in the database, has a wall budget of 240 seconds, and returns what it did not finish to the queue; the queue is never a step argument. On the Pro plan the limit is 800 seconds and the budget 600.

1. Discover. Fetch `robots.txt` from every origin of the site's own hosts, over https and http, and every sitemap, parse robots.txt into rules and the sitemaps into entries with their `lastmod` and children, and run the robots and sitemap checks. Seed `audit_queue` with the home page of every locale at click depth 0 and the sitemap URLs; the first Read step fetches the home pages, so robots.txt is known before any page is asked for. Done when the queue holds the home pages and the sitemap URLs and the robots rules are stored on the audit.
2. Read, 50 URLs per step at 5 requests a second, one click depth at a time. Each page is fetched with the hop chain recorded, parsed, run through the page checks and the shell test, written to `site_pages` with its depth, body hash, inbound link count and shell answer, and its failures to `audit_findings`; its internal links join the queue, breadth first, parameters capped at 50 per path. The step writes the pages read so far to the audit and `progressed_at` to the run. Done when the queue is empty or 5 000 URLs have been read.
3. Resources and external links, 50 URLs per step. HEAD every distinct internal image once, and every distinct external link once at 2 requests a second per foreign host, and write the failures. Done when every distinct URL has an answer or a recorded refusal.
4. Render, which waits for the render module, as the Delivery section of `audit.md` says. Pick the sample, fetch it raw with a phone's user agent and store the extract, mint the render token, create the sandboxes with the URLs and the token, start the render script detached, and return. The workflow then waits on a hook; the render route stores each page's extract in `audit_renders` and resumes the hook when a sandbox reports done. A step ends the sandboxes, clears the token, HEADs the sample's scripts and stylesheets, and runs the checks that compare raw with rendered and phone with desktop. When the site is a shell, by the answers the Read step stored and the rule of `audit.md`, the same step creates 10 sandboxes for every page read before waiting. Done when every sampled page has a rendered result or a recorded failure, and no sandbox is running.
5. Site checks. Compare the sitemap set with the crawl set both ways, find duplicates, orphans, hreflang clusters and canonical targets across pages, probe host variants on a sample of 20 paths, fetch the home page with each AI search agent's user agent for the CDN test, and run the GEO and markdown hints. Done when every site-level check has a result.
6. Score. Count passes and failures per check with the project's intended marks applied, compute the score and the gate, the counters, the comparison with the last finished audit on the checks both ran, the measurements and the cost, write them to the audit through `score_audit`, store whether the site is a shell, mark the pages a complete audit did not meet as gone, run the retention sweep, and end the run as `finished`. Done when the Audit section shows the score.

Every step writes `progressed_at`, and so does the render route, and a run with no progress for 15 minutes counts as stalled, the rule of every run. Stop in the Audit section cancels the Workflow run by its id, ends the sandboxes, ends the run as `failed` with the message "You stopped the audit." and, when that update ended the run, calls `stop_audit`, a `security definer` function that marks the audit partial; then the action scores the pages read with the code of step 6, without the checks that compare pages, and writes the score through `score_audit`, the function the intended mark uses. A score that fails to write leaves the stopped audit unscored. A step still running when Stop lands finishes its URLs; the next step sees the run is no longer running and returns, and a run that has ended is never ended again. Twenty 429, 5xx or time-out answers in a row end the run as `failed` with the message that the site stopped answering or rate-limited the audit. The sandbox's CPU seconds and GB-hours are priced from the unit prices kept beside the model prices and added to the run's `cost_usd`.

## Publishing

A page has two versions: the working copy in `pages`, which the editor saves, and the published version in `published_pages`, which the API, the sitemaps and the webhook read. A page is live when its `status` is `published`; only live pages reach the site.

Publish, Unpublish and Discard changes are Server Actions. Each first checks, through `getCurrentUser()` and the session client, that the signed-in user owns the project. Publish and Unpublish then call one module, `features/publishing/`, which renders and sanitizes the HTML on the server and writes with the admin client, through SQL functions granted to the service role alone. No SQL function the browser can call takes HTML, and the browser has no write on `published_pages`; on `pages` it writes only the fields the editor holds. In auto mode, when it comes with the weekly run, the run's Outcome step calls the same module for every clean translation group.

The card shows Publish on a draft or an unpublished page, Publish changes and Discard changes on a live page whose copy differs from its version, and Unpublish on a live page. The editor and the Pages table mark a page with unpublished changes: its `content_hash` differs from its published version's. While the editor holds edits that are not saved, Publish, Publish changes and Discard changes are off, with the sentence "Save the page first, then publish it.", because each acts on the saved copy. A page whose `status` is `published` with no published version, from before step 5, offers no Discard changes and says that Publish changes writes its first version.

The editor also shows a line with the page's language versions, each with its state: draft, live, live with unpublished changes, or unpublished. A version carries a mark when another live version of its group has a later `modified_at`, because its translation may be out of date. The mark clears when this version gets a later `modified_at` itself. The Pages table marks a row whose language versions diverge: they are in different states, or one of them carries the mark. Only the weekly run writes several versions of one page, so until it ships the line shows one version.

Publish acts on one page from the dashboard and on one translation group from the weekly run. Either is one action: one transaction and one webhook event.

1. Check. The page has an author, by default its kind's; without one the button is off, with a sentence that says what to fill in. A page published before keeps its address: when the URL computed from today's base URL, URL prefix and slug differs from the published one, its host or its path, Publish refuses with a sentence that names both addresses, because a new address needs a redirect from the old one, which waits in the backlog. A page with a `check_note` publishes after a dialog that repeats the note and asks the owner to confirm it. Done when every page of the action may go out.
2. Render `body_html` from `body_md` with the one renderer, under the HTML contract of [`content-api.md`](content-api.md), with the `toc`, the word count and `body_hash` of the rendered body. Done when the HTML passed the sanitizer.
3. Write the published versions from the working copies, in one transaction: every field the API serves, the HTML, the path and the URL, `content_hash`, and `text_hash` of the title, the body and the FAQ, which the write computes from the copy it locks. A working copy saved since it was rendered no longer matches its `content_hash`, so the write refuses it and Publish asks the owner to try again. `modified_at` on the first publication and when `text_hash` differs from the version it replaces; `updated_at` always, the clock of the sync. On `pages`, each page gets `status` `published`, `published_at` the first time, and loses `unpublished_at` and `redirect_to`; a page with no author of its own gets the author it went live with, its kind's, before its `content_hash` is copied, so both versions hold the same author and the same hash. When a page was not live before, every other live language version of its group outside the action gets a new `updated_at`, because its `alternates` changed. Done when the transaction committed. The pages are live from that moment.
4. Start the after-publish Workflow. Done when its run started.

The after-publish Workflow runs its steps with retries. The publication stays as it is when any of it fails, with no rollback. A run that does not start shows at once, in a sentence by the button the owner clicked, which says the page is live and the site was not told. A step that still fails after its retries shows where its work shows: a delivery in the webhook log and a ping in the IndexNow log of Settings, Integration. A failed cache step leaves only the server's log, because the cache expires on its own within its lifetime of 15 minutes, which [`content-api.md`](content-api.md) gives under "Caching".

1. Clear the project's cache of API answers. Done when the next request reads the new version.
2. Deliver the webhook when the project has a URL and the webhook is on. One event for the action: `page.published` when a page of it was not live before, else `page.updated`. The action's pages go in `data.pages`, and the live versions outside the action whose `alternates` changed go in `data.updated`. Done when the delivery's Workflow run started.
3. Ping IndexNow when the switch is on, with the URL of each page that was not live before or whose `body_hash` changed. Done when the ping's Workflow run started.

Discard changes asks first, in a dialog that says the changes cannot be brought back, because no history keeps them. It then copies the published version's editor fields, never the slug, back into the working copy with one update, in the owner's session, because it writes only the fields the editor holds. Done when the update committed; the two `content_hash` values then match.

A kind's author is a page's default only until the page's first publication. From then on the page has its own author, so a later change of the kind's author reaches drafts and no live page, while an edit of an author's own data reaches every live page that shows the author.

Unpublish: the owner picks 410 or a redirect, to a path on the site or a full https URL with no user name or password. A path is stored as an absolute URL on the page's own host, and a full URL as it parses on its own. A redirect to the page's own address is refused, because it would loop. In one transaction of the publishing module, the page gets `status` `unpublished`, `unpublished_at` and `redirect_to`, and its published version and the other live language versions get a new `updated_at`. So the sync returns the page's removal record and its siblings without it in `alternates`. The page is gone once the transaction commits. The after-publish Workflow then clears the cache, delivers `page.unpublished` with the redirect, and pings IndexNow with the old URL. The working copy stays. A later Publish publishes it as it stands, drops the redirect, and counts as a page that was not live before.

An edit in Settings of an author, the organization, a kind or a locale changes what the API answers for every live page that shows it. A kind's author is not among these edits, because a live page holds its own author. The Settings action saves the edit, then calls the publishing module, which moves `updated_at` of those pages' published versions and starts the after-publish Workflow. It clears the cache and sends one `page.updated` with `data.pages` empty and those pages in `data.updated`. `modified_at` does not move and IndexNow gets no ping, as with sibling language versions. The crawl moves the live pages through the same call of the module, so it starts the same Workflow, when it changes what they show, in steps 4 and 6 of the crawl; a run that does not start there shows only in the server's log, because no one clicked.

A webhook delivery is a Workflow run per event. Each attempt is a step with no retries of its own, which writes a row of `webhook_deliveries`; between attempts the run sleeps by the schedule in [`content-api.md`](content-api.md), which costs no compute. Each attempt reads the URL and the secrets again and signs with its own `webhook-timestamp`; the run stops when the webhook is off or the URL is empty. The POST goes through the guarded fetch with its body, https only and no redirects followed, within 15 seconds, and keeps the first 1 KB of the answer. A 410 turns the webhook off, and so do 5 days since the first failed attempt with no 2xx since. While the webhook is off, no new run starts. Redeliver starts a new run with the same event id, and Send test event a run with `webhook.test`. Done when an attempt got a 2xx or the schedule ended.

The IndexNow key file is checked through the guarded fetch with no redirect followed: a host passes when its own `/<key>.txt` answers 200 with the key. Settings check every host among the locales' base URLs when the owner asks, and a ping checks a host that has no passed check first. A ping answered 403 clears the host's check. A ping runs as a Workflow per host. When a URL in it was pinged less than 10 minutes ago, the run sleeps until 10 minutes after that ping, then sends, so a change is never dropped. A 429 makes it wait for `Retry-After`, or 10 minutes. `indexnow_pings` keeps every answer, so the 429 answers of a project are a count. Done when the answer is stored in `indexnow_pings`.
